# @qudag/core Buffer Strategy

## Overview

This document details the buffer management and zero-copy strategies for `@qudag/core` N-API bindings. Efficient buffer handling is critical for performance, especially for cryptographic operations involving large keys, signatures, and quantum state vectors.

## Goals

1. **Zero-Copy Operations**: Minimize memory copies between Rust and JavaScript
2. **Memory Safety**: Ensure no use-after-free or data races
3. **Performance**: Target <5% overhead compared to native Rust operations
4. **Ergonomics**: Provide natural JavaScript Buffer/TypedArray APIs

## Zero-Copy Strategy

### 1. Rust-Owned, JavaScript-Viewed Buffers

**Use Case:** Cryptographic keys, signatures, and other immutable data generated by Rust.

**Implementation:**

```rust
use napi::bindgen_prelude::*;

#[napi]
impl MlDsaKeyPair {
    /// Return public key as zero-copy Uint8Array
    #[napi]
    pub fn public_key(&self) -> Uint8Array {
        // Create Uint8Array backed by Rust-owned buffer
        // The buffer remains owned by self.inner
        // JavaScript gets a view that remains valid while self is alive
        Uint8Array::new(self.inner.public_key().to_vec())
    }

    /// Alternative: External buffer with finalizer
    #[napi]
    pub fn public_key_external(&self, env: Env) -> Result<JsBuffer> {
        // Create external buffer backed by Rust allocation
        let bytes = self.inner.public_key();
        let len = bytes.len();

        unsafe {
            // SAFETY: Buffer is valid for the lifetime of self
            // Finalizer ensures cleanup when JavaScript releases the buffer
            env.create_buffer_with_borrowed_data(
                bytes.as_ptr() as *const u8,
                len,
                bytes as *const [u8] as *mut c_void,
                |_env, data| {
                    // Finalizer: called when JavaScript GCs the buffer
                    // In this case, data is borrowed from self, so no cleanup needed
                },
            )
            .map(|b| b.into_raw())
        }
    }
}
```

**Benefits:**
- No memory copy from Rust to JavaScript
- Rust retains ownership and control
- Automatic cleanup via finalizers

**Trade-offs:**
- JavaScript buffer is invalidated if Rust object is dropped
- Requires careful lifetime management

**Safety Considerations:**
- Ensure Rust object outlives JavaScript buffer view
- Use Arc<T> for shared ownership across threads
- Document lifetime requirements in TypeScript definitions

### 2. JavaScript-Owned, Rust-Borrowed Buffers

**Use Case:** User-provided payloads, configuration data, temporary inputs.

**Implementation:**

```rust
#[napi]
impl QuantumDAG {
    #[napi]
    pub async fn add_message(&self, payload: Buffer) -> Result<String> {
        // Borrow JavaScript buffer without copying
        let payload_slice: &[u8] = payload.as_ref();

        // Clone for async operation (required for safety)
        let payload_vec = payload_slice.to_vec();

        let dag = Arc::clone(&self.inner);

        crate::runtime::spawn_blocking(move || {
            let mut dag = dag.blocking_write();
            dag.add_message(payload_vec)
                .map_err(|e| Error::from_reason(format!("Failed to add message: {}", e)))?;

            let vertex_id = qudag_dag::VertexId::from_bytes(payload_vec);
            Ok(hex::encode(vertex_id.as_bytes()))
        })
        .await
        .map_err(|e| Error::from_reason(format!("Task join error: {}", e)))?
    }
}
```

**Why Clone for Async:**
JavaScript buffers may be garbage collected or modified during async operation. Cloning ensures safety.

**Alternative: Zero-Copy with Pinning:**

```rust
use napi::bindgen_prelude::*;
use std::pin::Pin;

#[napi]
pub fn process_large_buffer(buffer: Buffer) -> Result<()> {
    // For synchronous operations, can borrow without cloning
    let data: &[u8] = buffer.as_ref();

    // Process data without copying
    process_quantum_state(data)?;

    Ok(())
}
```

**Benefits:**
- True zero-copy for synchronous operations
- No Rust allocation for JavaScript-provided data

**Trade-offs:**
- Must clone for async operations
- Requires synchronous processing or careful lifetime management

## Buffer Pool Strategy

### Motivation

Many QuDAG operations use fixed-size buffers repeatedly:
- ML-DSA signature verification: 3,309 bytes
- Key generation: 1,952 bytes (public), 4,032 bytes (secret)
- Ciphertext: 1,088 bytes

Allocating and deallocating these buffers on every operation adds overhead.

### Implementation

```rust
use std::collections::VecDeque;
use std::sync::Mutex;
use once_cell::sync::Lazy;

/// Buffer pool for common sizes
struct BufferPool {
    pools: Vec<Mutex<VecDeque<Vec<u8>>>>,
    sizes: Vec<usize>,
}

static BUFFER_POOL: Lazy<BufferPool> = Lazy::new(|| {
    BufferPool::new(vec![
        32,    // Shared secrets, hashes
        1088,  // ML-KEM ciphertext
        1184,  // ML-KEM public key
        1952,  // ML-DSA public key
        2400,  // ML-KEM secret key
        3309,  // ML-DSA signature
        4032,  // ML-DSA secret key
    ])
});

impl BufferPool {
    fn new(sizes: Vec<usize>) -> Self {
        let pools = sizes.iter().map(|_| Mutex::new(VecDeque::new())).collect();
        Self { pools, sizes }
    }

    /// Acquire a buffer of the given size
    fn acquire(&self, size: usize) -> Vec<u8> {
        // Find pool for this size
        if let Some(idx) = self.sizes.iter().position(|&s| s == size) {
            if let Ok(mut pool) = self.pools[idx].lock() {
                if let Some(mut buffer) = pool.pop_front() {
                    // Reuse existing buffer
                    buffer.clear();
                    buffer.resize(size, 0);
                    return buffer;
                }
            }
        }

        // No buffer available, allocate new
        vec![0u8; size]
    }

    /// Return a buffer to the pool
    fn release(&self, mut buffer: Vec<u8>) {
        let size = buffer.capacity();

        // Find pool for this size
        if let Some(idx) = self.sizes.iter().position(|&s| s == size) {
            if let Ok(mut pool) = self.pools[idx].lock() {
                // Limit pool size to prevent unbounded growth
                if pool.len() < 64 {
                    buffer.clear();
                    pool.push_back(buffer);
                }
                // Otherwise, buffer is dropped and deallocated
            }
        }
    }
}

/// RAII guard for pooled buffers
pub struct PooledBuffer {
    buffer: Option<Vec<u8>>,
}

impl PooledBuffer {
    pub fn acquire(size: usize) -> Self {
        Self {
            buffer: Some(BUFFER_POOL.acquire(size)),
        }
    }

    pub fn as_slice(&self) -> &[u8] {
        self.buffer.as_ref().unwrap()
    }

    pub fn as_mut_slice(&mut self) -> &mut [u8] {
        self.buffer.as_mut().unwrap()
    }
}

impl Drop for PooledBuffer {
    fn drop(&mut self) {
        if let Some(buffer) = self.buffer.take() {
            BUFFER_POOL.release(buffer);
        }
    }
}
```

### Usage in Bindings

```rust
#[napi]
impl MlDsaPublicKey {
    #[napi]
    pub fn verify(&self, message: Buffer, signature: Buffer) -> Result<bool> {
        // Use pooled buffer for internal operations
        let mut working_buffer = PooledBuffer::acquire(3309);

        // Perform verification
        match self.inner.verify(&message, &signature) {
            Ok(()) => Ok(true),
            Err(_) => Ok(false),
        }
        // working_buffer automatically returned to pool on drop
    }
}
```

**Benefits:**
- Reduced allocation overhead
- Better cache locality
- Lower GC pressure

**Trade-offs:**
- Memory overhead for pooled buffers
- Thread contention on pool locks (mitigated by per-size pools)

## TypedArray vs ArrayBuffer vs Buffer

### Comparison

| Type | Use Case | Performance | API |
|------|----------|-------------|-----|
| `Buffer` | Node.js standard, crypto operations | Excellent | Rich API, widely used |
| `Uint8Array` | Web standard, cross-platform | Excellent | Standard TypedArray API |
| `ArrayBuffer` | Raw bytes, shared memory | Good | Low-level, requires views |

### Recommendation

**Use `Uint8Array` for all cryptographic buffers:**

```typescript
interface MlDsaKeyPair {
    publicKey(): Uint8Array;
    sign(message: Buffer): Uint8Array;
}
```

**Rationale:**
- Cross-platform (Node.js and potential future browser support)
- Zero-copy compatible with both `Buffer` and `ArrayBuffer`
- Standard TypedArray methods available
- Interoperable with Node.js `Buffer` via `Buffer.from(uint8array)`

### Conversion Strategies

```typescript
// Uint8Array ⟷ Buffer (zero-copy)
const uint8 = new Uint8Array([1, 2, 3]);
const buffer = Buffer.from(uint8.buffer, uint8.byteOffset, uint8.byteLength);

// Buffer ⟷ Uint8Array (zero-copy view)
const buffer2 = Buffer.from([1, 2, 3]);
const uint8_2 = new Uint8Array(buffer2.buffer, buffer2.byteOffset, buffer2.byteLength);
```

## Memory Safety Patterns

### Pattern 1: Borrowed References (Sync)

```rust
#[napi]
pub fn hash_data(data: Buffer) -> Result<Uint8Array> {
    // Synchronous operation: safe to borrow
    let input: &[u8] = data.as_ref();

    // Compute hash without copying input
    let hash = blake3::hash(input);

    // Return owned result
    Ok(Uint8Array::new(hash.as_bytes().to_vec()))
}
```

**Safety:** Input buffer cannot be freed during synchronous operation.

### Pattern 2: Cloned Data (Async)

```rust
#[napi]
pub async fn verify_signature_async(
    &self,
    message: Buffer,
    signature: Buffer,
) -> Result<bool> {
    // Clone for async operation
    let msg_vec = message.to_vec();
    let sig_vec = signature.to_vec();

    let pk = self.inner.clone();

    crate::runtime::spawn_blocking(move || {
        // Safe: owned data
        pk.verify(&msg_vec, &sig_vec)
            .map(|_| true)
            .or(Ok(false))
    })
    .await
    .map_err(|e| Error::from_reason(format!("Join error: {}", e)))?
}
```

**Safety:** Cloned data outlives the async operation.

### Pattern 3: Arc-Wrapped Buffers (Shared)

```rust
use std::sync::Arc;

#[napi]
pub struct SharedBuffer {
    data: Arc<Vec<u8>>,
}

#[napi]
impl SharedBuffer {
    #[napi(factory)]
    pub fn new(data: Buffer) -> Self {
        Self {
            data: Arc::new(data.to_vec()),
        }
    }

    #[napi]
    pub fn as_bytes(&self) -> Uint8Array {
        // Zero-copy view into Arc-wrapped data
        Uint8Array::new(self.data.as_ref().clone())
    }

    #[napi]
    pub async fn process(&self) -> Result<()> {
        let data = Arc::clone(&self.data);

        crate::runtime::spawn(async move {
            // Safe: Arc keeps data alive
            process_large_buffer(&data).await
        })
        .await
        .map_err(|e| Error::from_reason(format!("Join error: {}", e)))?
    }
}
```

**Safety:** Arc reference counting ensures buffer outlives all operations.

## Quantum State Vector Handling

### Challenge

Quantum operations may involve large state vectors (up to several MB for simulations). Copying these on every N-API call is prohibitively expensive.

### Strategy: Pinned Rust Ownership

```rust
use std::sync::Arc;
use parking_lot::RwLock;

#[napi]
pub struct QuantumState {
    // State vector remains in Rust memory
    state: Arc<RwLock<Vec<f64>>>,
    dimension: usize,
}

#[napi]
impl QuantumState {
    #[napi(factory)]
    pub fn new(dimension: u32) -> Self {
        let size = 1 << dimension; // 2^dimension
        Self {
            state: Arc::new(RwLock::new(vec![0.0; size])),
            dimension: dimension as usize,
        }
    }

    /// Get read-only view of state vector (zero-copy)
    #[napi]
    pub fn get_amplitudes(&self) -> Float64Array {
        let state = self.state.read();
        // Return view into Rust-owned buffer
        // WARNING: This is only safe if state is pinned
        Float64Array::new(state.clone())
    }

    /// Apply quantum gate (in-place, no copying)
    #[napi]
    pub async fn apply_gate(&self, gate_matrix: Float64Array) -> Result<()> {
        let state = Arc::clone(&self.state);
        let matrix = gate_matrix.to_vec();

        crate::runtime::spawn_blocking(move || {
            let mut state = state.write();
            apply_quantum_gate(&mut state, &matrix)?;
            Ok(())
        })
        .await
        .map_err(|e| Error::from_reason(format!("Join error: {}", e)))?
    }
}
```

**Benefits:**
- State vector never copied between Rust and JavaScript
- All operations occur in-place in Rust memory
- JavaScript can request read-only views for inspection

**Trade-offs:**
- Complex lifetime management
- Requires careful documentation of view validity

## Memory Management Best Practices

### 1. Explicit Cleanup for Sensitive Data

```rust
#[napi]
impl MlDsaKeyPair {
    /// Explicitly zeroize secret key material
    #[napi]
    pub fn destroy(&mut self) {
        // Zeroize is handled by Drop impl in qudag_crypto
        // But allow explicit cleanup
        drop(std::mem::take(&mut self.inner));
    }
}
```

### 2. Buffer Size Limits

```rust
const MAX_PAYLOAD_SIZE: usize = 10 * 1024 * 1024; // 10 MB

#[napi]
impl QuantumDAG {
    #[napi]
    pub async fn add_message(&self, payload: Buffer) -> Result<String> {
        if payload.len() > MAX_PAYLOAD_SIZE {
            return Err(Error::from_reason(format!(
                "Payload too large: {} bytes (max: {})",
                payload.len(),
                MAX_PAYLOAD_SIZE
            )));
        }

        // Process payload...
    }
}
```

### 3. Bounded Buffer Pools

```rust
impl BufferPool {
    const MAX_POOL_SIZE: usize = 64;
    const MAX_TOTAL_MEMORY: usize = 64 * 1024 * 1024; // 64 MB

    fn release(&self, buffer: Vec<u8>) {
        let size = buffer.capacity();

        if let Some(idx) = self.sizes.iter().position(|&s| s == size) {
            if let Ok(mut pool) = self.pools[idx].lock() {
                if pool.len() < Self::MAX_POOL_SIZE {
                    // Check total memory usage
                    let current_total: usize = pool.iter().map(|b| b.capacity()).sum();
                    if current_total + size <= Self::MAX_TOTAL_MEMORY {
                        pool.push_back(buffer);
                        return;
                    }
                }
            }
        }
        // Buffer is dropped and deallocated
    }
}
```

### 4. Finalizers for External Resources

```rust
use napi::bindgen_prelude::*;

#[napi]
impl NetworkManager {
    #[napi]
    pub fn finalize(mut self, _env: Env) -> Result<()> {
        // Clean up resources when JavaScript object is GC'd
        let manager = Arc::clone(&self.inner);

        // Spawn cleanup on runtime
        crate::runtime::spawn(async move {
            let _ = manager.write().await.shutdown().await;
        });

        Ok(())
    }
}
```

## Security Considerations

### Constant-Time Operations

Ensure cryptographic operations remain constant-time across N-API boundary:

```rust
#[napi]
impl MlDsaPublicKey {
    #[napi]
    pub fn verify(&self, message: Buffer, signature: Buffer) -> Result<bool> {
        // Use constant-time verification
        let result = self.inner.verify(&message, &signature);

        // Return boolean without early exit based on secret data
        match result {
            Ok(()) => Ok(true),
            Err(_) => Ok(false), // Don't leak error details that could aid timing attacks
        }
    }
}
```

### Buffer Zeroization

Ensure sensitive buffers are zeroized on drop:

```rust
use zeroize::Zeroize;

#[napi]
pub struct SecretKeyBuffer {
    data: Vec<u8>,
}

impl Drop for SecretKeyBuffer {
    fn drop(&mut self) {
        self.data.zeroize();
    }
}
```

### Read-Only Views

Prevent accidental mutation of sensitive data:

```rust
#[napi]
impl MlDsaKeyPair {
    #[napi]
    pub fn public_key(&self) -> Uint8Array {
        // Return Uint8Array, not Buffer
        // Uint8Array is immutable from JavaScript perspective
        Uint8Array::new(self.inner.public_key().to_vec())
    }
}
```

## Conclusion

This buffer strategy provides:

1. **Zero-Copy Performance**: Minimal overhead through Rust-owned views
2. **Memory Safety**: Proper lifetime management and Arc-based sharing
3. **Resource Efficiency**: Buffer pooling for common sizes
4. **Security**: Zeroization and constant-time guarantees
5. **Flexibility**: Support for both sync and async operations

The strategy enables near-native performance for QuDAG's cryptographic operations while maintaining the safety guarantees of Rust and the ergonomics of JavaScript.
